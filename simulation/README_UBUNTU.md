# ORCHESTRA hybrid simulation on Ubuntu

I use this guide to run the ORCHESTRA MQTT, dashboard, model-bridge, and ESP32
demonstrator on Ubuntu. Robot 1 can use MQTT telemetry from the ESP32; robots
2–10 are deterministic synthetic streams generated by the gateway.

## Install the local toolchain

```bash
sudo apt update
sudo apt install -y git curl python3 python3-pip python3-venv mosquitto mosquitto-clients
```

I also install Node.js LTS, VS Code with PlatformIO, and Docker/Compose when I
want to use the containerized broker. I keep the broker on a private
laboratory network.

## Daily startup

1. Connect the PC and ESP32 to the same isolated access point.
2. Find the PC IPv4 address:

```bash
ip -4 addr
```

3. Put that address in the ignored firmware configuration. The ESP32 must not
   use `127.0.0.1` because that refers to the ESP32 itself.
4. Start Mosquitto:

```bash
cd simulation
mosquitto -c mosquitto/mosquitto.conf -v
```

5. In another terminal, observe the topics:

```bash
mosquitto_sub -h 127.0.0.1 -p 1883 -t 'orchestra/#' -v
```

6. Start the dashboard and model bridge:

```bash
cd src/ui
npm install
npm run dev:stack
```

7. Open `http://localhost:3000`. Robot 1 should appear as `MQTT` after its
   first packet; robots 2–10 should appear as `SIM`.

## Configure the dashboard

I create `.env.local` once and keep it outside Git:

```bash
cd src/ui
cp .env.example .env.local
```

The minimum values are:

```env
MQTT_BROKER_URL=mqtt://127.0.0.1:1883
MQTT_TOPIC=orchestra/laser-welding/+/telemetry
MQTT_COMMAND_TOPIC=orchestra/laser-welding/{device_id}/command
ORCHESTRA_LIVE_DEVICE_ID=esp32-wroom32-laser-01
ORCHESTRA_STATION_ID=CN-SUZHOU-LW-01
ORCHESTRA_MODEL_URL=http://127.0.0.1:8787/score
```

## Configure and flash the ESP32

```bash
cp src/firmware/include/config.example.h src/firmware/include/config.local.h
```

I edit the ignored local file with the private Wi-Fi values and the current PC
IPv4 address:

```cpp
#define WIFI_SSID "LAB_NETWORK_NAME"
#define WIFI_PASSWORD "LAB_NETWORK_PASSWORD"
#define MQTT_BROKER_HOST "PC_IPV4_ADDRESS"
#define MQTT_DEVICE_ID "esp32-wroom32-laser-01"
#define MQTT_STATION_ID "CN-SUZHOU-LW-01"
#define USE_SIMULATED_SENSORS true
```

I build, upload, and monitor:

```bash
cd src/firmware
pio run
pio run --target upload
pio device monitor
```

With an already flashed board, I can open `/dev/ttyUSB0` directly:

```bash
pio device monitor -p /dev/ttyUSB0 -b 115200
```

`USE_SIMULATED_SENSORS=true` validates transport and payload handling. It does
not represent calibrated physical sensors.

## Production orders and scenarios

In Operations, I can enter a production target on the first visit, follow
shift/checkpoint progress, reset the simulation, schedule maintenance, restore
robot/firmware lifetime, and inspect the three agent decisions in Model
Observatory.

The ESP32 scenario control supports `normal`, `low_shielding_gas`,
`lens_contamination`, `focal_offset`, `fixture_vibration`, and
`high_laser_power`.

These are demonstrator controls. They do not provide machine safety authority.

## Firewall and troubleshooting

If the ESP32 is on the private access point, I allow TCP 1883 only on that
network:

```bash
sudo ufw allow from PRIVATE_LAB_SUBNET to any port 1883 proto tcp
sudo ufw status
```

I use `mosquitto_sub` to confirm traffic, restart Next.js after editing
`.env.local`, and check the serial monitor if the ESP32 connects to Wi-Fi but
does not publish. If the development bundle is stale, I stop Next.js, remove
only `src/ui/.next`, and run `npm run dev:stack` again.

## Shutdown

I stop Next.js and Mosquitto with `Ctrl+C`. If I used Docker Compose instead,
I run `docker compose down` after the laboratory session.
